# ทดลองทำ Index บนฐานข้อมูลของ Bookvice

งานที่ได้รับ: ทดลองทำ indexing บนฐานข้อมูล แล้วนำไปประยุกต์ใช้กับโปรเจกต์ตัวเอง
(ตามแล็บตัวอย่าง `indexing-lab_02` ของอาจารย์)

แล็บตัวอย่างใช้ตาราง `transactions` สมมติ งานนี้ใช้โครงเดียวกัน
แต่เปลี่ยนเป็น**ตารางและ query ที่ Bookvice ยิงจริง** แล้วเอาผลไปแก้โปรเจกต์จริง

- โค้ดแล็บ: [`indexing-lab/`](../indexing-lab/) — ดับเบิลคลิก `run-lab.bat` รันซ้ำได้ทั้งชุด
- ผลดิบ: [`indexing-lab/results/`](../indexing-lab/results/) (รอบที่ 2) และ `results/round1/` (รอบที่ 1)

## สรุปสั้น

| | ก่อน | หลัง |
|---|---|---|
| หน้าที่ผู้ใช้เปิดบ่อยที่สุด 9 หน้า (ข้อมูล 1 ล้านคิว) | 7–97 ms | **0.02–1.3 ms** |

## 2. รอบที่ 1 — ลองแล้วไม่ตรงกับที่คาดหลายข้อ

ออกแบบ index รอบแรกจากการอ่านโค้ด แล้ววัดจริง ผลที่ไม่ตรงกับที่คาด:

| ที่คาดไว้ | ที่วัดได้จริง | ตัดสินใจ |
|---|---|---|
| ทำ index ผสม (user_id, booking_date, booking_time) ให้หน้า "การจองของฉัน" จะเร็วขึ้นมาก | 0.041 ms เทียบกับ index เดี่ยว 0.071 ms ต่างกันแค่ 0.03 ms เพราะลูกค้าแต่ละคนมีไม่กี่คิว แต่ index ใหญ่ขึ้นจาก 11 MB เป็น 30 MB | **กลับไปใช้ index เดี่ยว** |
| ทำ index ผสม (user_id, created_at) ให้กล่องแจ้งเตือน | 0.074 ms เทียบกับของเดิม 0.036 ms — ไม่ได้เร็วขึ้นเลย | **กลับไปใช้ index เดี่ยว** |
| หน้าจองต้องการ index (shop_id, booking_date) ใหม่ เพราะ index เดิมมี staff_id คั่นกลาง | PostgreSQL ใช้ index เดิม `uq_booking_held_slot` ได้อยู่แล้ว เพราะเป็น partial index เล็ก ๆ (4 MB) ที่ขึ้นต้นด้วย shop_id เร็วอยู่แล้วตั้งแต่ก่อนแก้ | แก้คอมเมนต์ในโค้ดที่เขียนผิดไว้ |
| index บน `status` (มี 4 ค่า) PostgreSQL ไม่เลือกใช้ | **ใช้จริง** เวลานับจำนวน (`count(*)` ใช้ Index Only Scan ได้ 30 ms) | ยังถอดออก แต่เปลี่ยนเหตุผล (หัวข้อ 5.3) |
| ระบบพักเงินจะเร็วขึ้นมากด้วย partial index | เร็วขึ้นแค่ 94 → 63 ms เพราะยังต้องไล่ทุกคิวที่เสร็จแล้ว (70% ของตาราง) | **แก้ที่ query แทน** (หัวข้อ 4) |

บทเรียนจากรอบนี้: **ออกแบบ index จากการเดาไม่พอ ต้องวัด** index ที่ดูดีในหัว
บางตัวไม่ช่วยอะไรเลยกับข้อมูลรูปแบบจริง และบางตัวที่คิดว่าไม่มีอยู่แล้วกลับช่วยได้

ผลดิบรอบที่ 1 เก็บไว้ที่ `indexing-lab/results/round1/`

## 3. รอบที่ 2 — ชุดสุดท้ายที่ใช้ในโปรเจกต์จริง

### ไม่มี index เทียบกับมี index

| ข้อ | หน้าเว็บ | ไม่มี index | มี index | เร็วขึ้น | วิธีที่ PostgreSQL ใช้ |
|---|---|---:|---:|---:|---|
| Q1 | หน้าจอง (ร้านจัดช่างให้) | 26.04 ms | 0.170 ms | 153× | Index Scan `ix_booking_held_slot` |
| Q1b | หน้าจอง (เลือกช่าง) | 27.16 ms | 0.015 ms | 1,810× | Index Scan `ix_booking_held_slot` |
| Q2 | การจองของฉัน | 25.19 ms | 1.262 ms* | 20× | Bitmap Index Scan `ix_bookings_user_id` |
| Q2b | นับคิวทั้งหมดของลูกค้า | 22.52 ms | 0.022 ms | 1,024× | Index Only Scan |
| Q3 | หน้าจัดการร้าน (22,184 คิว) | 26.67 ms | 0.560 ms | 48× | Index Scan **Backward** `ix_bookings_shop_date` |
| Q4 | รีวิวร้าน | 7.61 ms | 0.074 ms | 103× | Index Scan **Backward** `ix_reviews_shop_created` |
| Q5c | ระบบพักเงิน (แบบที่แก้แล้ว) | 53.79 ms | 0.049 ms | 1,098× | Index Scan PK + Index Only Scan `ix_payments_held` |
| Q6 | จุดแดงบนกระดิ่ง | 23.65 ms | 0.032 ms | 739× | Index Only Scan `ix_notif_unread` |
| Q7 | กล่องแจ้งเตือน | 25.34 ms | 0.106 ms | 239× | Bitmap Index Scan `ix_notifications_user_id` |

\* Q2 รอบนี้ index ยังไม่อยู่ในหน่วยความจำ ต้องอ่านจากดิสก์ 6 หน้า (เห็นใน `Buffers: shared read=6`)
ครั้งถัดไปที่อยู่ในหน่วยความจำแล้ววัดได้ 0.071 ms (`results/round1/03-old-vs-new_index.txt`)

ไม่มี index ทุกข้อเป็น **Parallel Seq Scan** คืออ่านทั้งล้านแถวด้วย CPU 3 ตัวพร้อมกัน
ถึงจะใช้หลาย CPU ก็ยังช้ากว่าการเปิด index ไปหาตรง ๆ หลายร้อยเท่า

### index ชุดเดิมของโปรเจกต์เทียบกับชุดใหม่

ชุดเดิม = index คอลัมน์เดียวที่ได้จาก `index=True` ทีละคอลัมน์ใน `models.py` ไม่ได้ออกแบบจาก query

| ข้อ | ชุดเดิม | ชุดใหม่ | ต่างกันเพราะ |
|---|---:|---:|---|
| Q1 หน้าจอง | 0.119 ms | 0.170 ms | ใช้ index ตัวเดียวกัน (ต่างกันแค่ความคลาดเคลื่อน) |
| Q3 หน้าจัดการร้าน | 4.31 ms | **0.56 ms** | ชุดเดิมต้องไล่ 4,209 แถวแล้วทิ้ง 4,108 แถวที่ไม่ใช่ร้านนี้ |
| Q4 รีวิวร้าน | 1.85 ms | **0.074 ms** | ชุดเดิมต้องดึงรีวิวทั้งร้าน 3,613 รายการมาเรียงก่อนตัดเหลือ 10 |
| Q5 ระบบพักเงิน | 90.68 ms | **0.049 ms** | แก้ index + แก้ query (หัวข้อ 4) |
| Q6 จุดแดงบนกระดิ่ง | 0.032 ms | 0.032 ms | เท่ากัน แต่ partial index เล็กกว่า (3 MB) |

| ขนาด index | ชุดเดิม | ชุดใหม่ |
|---|---:|---:|
| bookings | 64 MB | 80 MB |
| notifications | 53 MB | 36 MB |
| payments | 68 MB | 61 MB |
| reviews | 5.8 MB | 9.6 MB |
| **รวม** | **190.8 MB** | **186.6 MB** |

ชุดใหม่เร็วกว่าในหน้าที่สำคัญ โดยพื้นที่รวมไม่ได้เพิ่ม เพราะถอดตัวที่ไม่ช่วยออกไปพร้อมกัน

## 4. ระบบพักเงิน: index อย่างเดียวไม่พอ ต้องแก้ query

`release_due()` ใน `escrow.py` หาเงินที่ถึงเวลาปล่อยให้ร้าน ถูกเรียกทุกครั้งที่มีคนเปิดรายการจอง

| แบบ | ไม่มี index | มี index |
|---|---:|---:|
| Q5 รุ่นแรก: ตรวจทุกคิวในระบบ | 96.62 ms | 65.56 ms |
| Q5b ตรวจเฉพาะร้านเดียว (ร้านดัง 22,184 คิว) | 70.04 ms | 66.17 ms |
| **Q5c ตรวจเฉพาะ 10 คิวในหน้าที่เปิดอยู่** | 53.79 ms | **0.049 ms** |

ทำไม index ช่วยรุ่นแรกได้น้อย: partial index `ix_payments_held` ทำให้ฝั่ง payments เร็วขึ้น
(30 ms → 3.5 ms) แต่ฝั่ง bookings ยังต้องไล่คิวที่เสร็จแล้วทั้งหมด ซึ่งมี 718,299 คิว
หรือ 72% ของตาราง ค่าที่ซ้ำเยอะขนาดนี้ไม่มี index ไหนช่วยได้

แก้ที่ตัว query: หน้ารายการจองเห็นแค่ 10 คิว ก็ตรวจแค่ 10 คิวนั้น (`booking_ids`)
หน้ากระเป๋าเงินร้านตรวจแค่ร้านเดียว (`shop_id`) ผลที่ผู้ใช้เห็นเหมือนเดิมทุกอย่าง
เพราะคิวที่ไม่ได้เปิดดูก็ไม่มีใครเห็นสถานะเงินของมันอยู่ดี

ข้อจำกัดที่ยังเหลือ: Q5b หน้ากระเป๋าเงินของร้านที่มีคิวมากเป็นหมื่นยังใช้เวลา 66 ms
ยอมรับได้เพราะเปิดเฉพาะเจ้าของร้าน และไม่ได้เปิดบ่อยเท่าหน้ารายการจอง

## 5. กับดัก: มี index แต่ไม่ถูกใช้ (เจอในโค้ดเราเอง)

### 5.1 ครอบคอลัมน์ด้วยฟังก์ชัน — 48 เท่า

```sql
-- ❌ 4.924 ms : index ใช้ได้แค่ shop_id แล้วต้องคำนวณ to_char ทุกแถวของร้าน (ทิ้ง 21,234 แถว)
WHERE shop_id = 1 AND to_char(booking_date, 'YYYY-MM') = '2026-08'
-- ✅ 0.102 ms : ใช้ index ได้ทั้ง shop_id และช่วงวันที่
WHERE shop_id = 1 AND booking_date >= '2026-08-01' AND booking_date < '2026-09-01'
```

### 5.2 partial index ต้องเขียนเงื่อนไขให้ตรงกันทุกตัวอักษร — 227 เท่า

`ix_notif_unread` สร้างด้วย `WHERE is_read = false`
โค้ดเดิมเขียน `Notification.is_read.is_(False)` ซึ่ง SQLAlchemy แปลงเป็น `is_read IS false`

```sql
-- ✅ 0.166 ms : ตรงกับเงื่อนไขของ index ใช้ Index Only Scan
WHERE user_id < 2000 AND is_read = false
-- ❌ 37.719 ms : PostgreSQL ไม่ถือว่าตรงกัน ต้องไปอ่านแถวจริง 7,284 หน้า แล้วทิ้ง 8,500 แถว
WHERE user_id < 2000 AND is_read IS false
```

ความหมายของสองแบบเหมือนกันทุกประการ (คอลัมน์ไม่เป็น NULL) แต่ PostgreSQL เทียบเงื่อนไขกับ index
แบบตรงตัว จึงแก้โค้ดให้ใช้ `UNREAD = Notification.is_read == False` ร่วมกันทุกจุด
(`app/routers/notifications.py`)

### 5.3 คอลัมน์ค่าซ้ำเยอะ — index ถูกใช้แค่ตอนนับ

`bookings.status` มี 4 ค่า และ `completed` ครอง 72% ของตาราง

| query | มี index | ไม่มี index |
|---|---:|---:|
| `count(*) WHERE status = 'completed'` | 30.4 ms (Index Only Scan) | — |
| `sum(total_price) WHERE status = 'completed'` | 50.7 ms (**Seq Scan** — ไม่เลือกใช้ index) | 53.0 ms |

พอต้องอ่านข้อมูลจริงของแถว PostgreSQL ไม่ใช้ index นี้เลย และระบบเราไม่เคยค้นด้วย status
ตัวเดียว (ค้นคู่กับร้านหรือลูกค้าเสมอ ซึ่งมี index ของคอลัมน์นั้นอยู่แล้ว) จึงถอดออก

### 5.4 ตารางเล็ก ไม่ต้องทำ index

ค้นหาร้านด้วยคำ (`ILIKE '%คำ%'`) บนตาราง shops 2,000 แถว อ่านทั้งตารางใช้แค่ 0.759 ms
B-tree ใช้กับ `%` นำหน้าไม่ได้อยู่แล้ว และตารางเล็กขนาดนี้อ่านทั้งตารางเร็วกว่าเปิด index
ถ้าวันหนึ่งร้านเป็นแสน ค่อยพิจารณา pg_trgm (GIN index สำหรับค้นหาข้อความ)

### 5.5 กฎ leftmost

`ix_bookings_shop_date (shop_id, booking_date, booking_time)` ใช้ค้นด้วยวันที่อย่างเดียวไม่ได้
จึงยังเก็บ `ix_bookings_booking_date` ไว้ ซึ่งหน้าหาก๊วนรายวัน (`matches.py`) ใช้อยู่ — วัดได้ 0.529 ms

ในทางกลับกัน `ix_bookings_shop_id` (shop_id ตัวเดียว) ถูกถอดออก เพราะ index ผสมที่ขึ้นต้นด้วย
shop_id ใช้แทนได้ทุกกรณี มีไว้ก็ซ้ำซ้อน

## 6. สิ่งที่เปลี่ยนในโปรเจกต์จริง

ประกาศใน `app/models.py` (ฐานข้อมูลใหม่) และ `app/migrate.py` (ฐานข้อมูลที่มีอยู่แล้วบนเว็บจริง)
มีเทสต์ตรวจว่าชุดใหม่ถูกสร้างครบและตัวที่ถอดไม่กลับมา (`tests/test_booking_payment.py` หัวข้อ "index ของฐานข้อมูล")

### เพิ่ม

| index | ใช้กับ | ผลที่วัดได้ |
|---|---|---|
| `ix_bookings_shop_date (shop_id, booking_date, booking_time)` | หน้าจัดการร้าน | 4.31 → 0.56 ms |
| `ix_reviews_shop_created (shop_id, created_at)` | รีวิวหน้าร้าน | 1.85 → 0.074 ms |
| `ix_payments_held (booking_id) WHERE status='paid' AND released_at IS NULL` | ระบบพักเงิน | 2 MB เทียบกับ index ทั้งคอลัมน์ 28 MB |
| `ix_notif_unread (user_id) WHERE is_read = false` | จุดแดงบนกระดิ่ง | 3 MB · เร็วเท่าเดิม |

### ถอด

| index | เหตุผล |
|---|---|
| `ix_bookings_shop_id` | ซ้ำกับคอลัมน์แรกของ `ix_bookings_shop_date` |
| `ix_reviews_shop_id` | ซ้ำกับคอลัมน์แรกของ `ix_reviews_shop_created` |
| `ix_bookings_status` | ไม่มี query ไหนใช้ (หัวข้อ 5.3) |
| `ix_payments_status` | มีแค่ paid/refunded และเกือบทุกแถวเป็น paid |
| `ix_notifications_is_read` | มีแค่สองค่า |
| `ix_notif_user_unread (user_id, is_read)` | แทนด้วย partial index ที่เล็กกว่า |

### แก้ query

1. `notifications.py` — เขียน `is_read = false` ให้ตรงกับ partial index (หัวข้อ 5.2)
2. `escrow.py :: release_due` — ตรวจเฉพาะคิวที่เปิดดูหรือร้านเดียว แทนทั้งตาราง (หัวข้อ 4)

## 7. ต้นทุนของ index

### พื้นที่ (ชุดใหม่)

| ตาราง | ข้อมูล | index | index / ข้อมูล |
|---|---:|---:|---:|
| bookings | 112 MB | 80 MB | 71% |
| payments | 135 MB | 61 MB | 45% |
| notifications | 115 MB | 36 MB | 31% |
| reviews | 18 MB | 9.6 MB | 53% |

partial index ประหยัดมาก: `ix_payments_held` เก็บ 94,438 จาก 1,411,749 แถว ได้ 2 MB
เทียบกับ `ix_payments_booking_id` ทั้งคอลัมน์ 28 MB

### การเขียน (INSERT)

จองคิวใหม่ 100,000 รายการแล้ว ROLLBACK (`labs/05-insert-cost.sql`)

| | index บนตาราง bookings | เวลา | ต่อ 1 คิว |
|---|---:|---:|---:|
| ไม่มี index | 1 (PK) | 0.200 วินาที | 2 µs |
| มี index | 6 | 1.002 วินาที | 10 µs |

ช้าลง 5 เท่า แต่ต่อการจองหนึ่งครั้งเพิ่มแค่ 8 ไมโครวินาที ขณะที่การเปิดหน้าจองเร็วขึ้นหลายร้อยเท่า
และเว็บจองคิวโดยธรรมชาติมีคนเปิดดูมากกว่ากดจอง (ลูกค้าหนึ่งคนเปิดหน้าดูเวลาว่างหลายรอบก่อนจองหนึ่งครั้ง
และการเปิดหน้าร้านหนึ่งครั้งยิง Q1 14 รอบ เพื่อดูเวลาว่างล่วงหน้า 14 วัน) จึงคุ้ม — ตัวเลขสัดส่วนจริงยังไม่ได้วัด เพราะเว็บยังไม่มีผู้ใช้มากพอ
นี่คือเหตุผลเดียวกับที่ไม่ทำ index ทุกคอลัมน์: ทุกตัวที่ไม่ได้ใช้คือต้นทุนฟรี

### index ทุกตัวถูกใช้จริง

หลังรันแล็บ 01–04 ทุก index ในชุดใหม่มี `idx_scan` มากกว่า 0 (`results/06-usage_index.txt`)
บนเว็บจริงใช้คำสั่งเดียวกันนี้ตรวจหา index ที่ไม่มีใครใช้ได้เป็นระยะ

## 8. ข้อจำกัดของการทดลอง

- วัดครั้งเดียวต่อ query บนเครื่องเดียว ตัวเลขต่ำกว่า 0.2 ms คลาดเคลื่อนได้มากเมื่อเทียบกัน
  (เช่น Q1 ชุดเดิม 0.119 vs ชุดใหม่ 0.170 ทั้งที่ใช้ index ตัวเดียวกัน)
- ข้อมูลเป็นข้อมูลจำลอง รูปแบบการกระจายตั้งใจให้ใกล้ของจริง แต่ไม่ใช่ข้อมูลผู้ใช้จริง
- เว็บจริงอยู่บน Neon (PostgreSQL บนคลาวด์) ซึ่งมีความหน่วงของเครือข่ายเพิ่มอีกหลาย ms ต่อคำขอ
  index ช่วยส่วนที่ฐานข้อมูลคิด ไม่ได้ช่วยส่วนเวลาเดินทางของข้อมูล
- ตอนนี้เว็บจริงมีข้อมูลหลักร้อยแถว ยังไม่เห็นความต่างจาก index เลย ผลในเอกสารนี้คือสิ่งที่จะเกิด
  เมื่อมีผู้ใช้จริงจำนวนมาก
